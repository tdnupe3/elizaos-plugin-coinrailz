Autonomous Service Discovery for AI Agents
1. A2A Protocol Discovery

Current Practices: Google’s Agent2Agent (A2A) protocol is a leading standard for agent discovery and interoperability
a2a-protocol.org
a2a-protocol.org
. Every A2A-compliant agent (“server”) publishes an Agent Card – a JSON metadata file describing its identity, skills/capabilities, endpoint URL, and auth requirements
a2a-protocol.org
a2a-protocol.org
. By convention this is hosted at a well-known URI (e.g. /.well-known/agent-card.json) on the agent’s domain
a2a-protocol.org
a2a-protocol.org
. Real agents use these cards to learn what other agents can do. For example, an agent could fetch another’s agent-card.json to see what “skills” it offers (like an API of functions)
a2a-protocol.org
a2a-protocol.org
.

Discovery Mechanisms: In practice, agents find each other via: (a) Pre-known directories – curated registries of agent cards; (b) Open crawling – scanning known domains or endpoints; or (c) Manual configuration – being pre-loaded with specific agent URLs
a2a-protocol.org
. A2A’s spec anticipates registries/catalogs where agents are listed for discovery
a2a-protocol.org
. For instance, Lifie Hub (hub.lifie.ai) is a community-driven registry for A2A agents, allowing providers to register their agent’s card URL (it reportedly indexed ~100 agents, though many turned out to be stub listings)
github.com
github.com
. Similarly, Google Cloud is launching an AI Agent Marketplace for enterprise customers, where partners can publish A2A agents for others to discover and purchase
cloud.google.com
cloud.google.com
. In enterprise settings, discovery is often “curated” – admins maintain an internal catalog of approved agent services
github.com
github.com
.

Agent Card Content: To maximize discoverability, your agent’s card should comprehensively list its capabilities and usage info. Include a clear name and description explaining the agent’s purpose and services
a2a-protocol.org
. Under skills, enumerate each actionable capability or API your platform provides (e.g. “fetch multi-chain balance”, “token sentiment analysis”) with descriptors. Use the provider field to identify your platform and a documentationUrl if available
a2a-protocol.org
a2a-protocol.org
. Agents also share how to authenticate – e.g. if tokens or API keys are needed – via the securitySchemes field
a2a-protocol.org
 (though ideally your services are open to pay-per-use without further auth). Ensuring your Agent Card follows the A2A spec v0.3 exactly will make it easier for any A2A-compliant crawlers to parse it
a2a-protocol.org
a2a-protocol.org
.

Are Agents Actively Crawling A2A? Today, fully autonomous A2A discovery is still in early stages. Many “agents” in the wild (e.g. Truth Terminal or certain AI trading bots) were bespoke and not using A2A – they interacted with predefined APIs and on-chain contracts given by their creators. However, the ecosystem is moving towards dynamic discovery. Google’s own Agent Development Kit (ADK) now supports A2A out-of-the-box, letting developers expose any agent as A2A-discoverable or load a partner’s Agent Card as a sub-agent
cloud.google.com
cloud.google.com
. This means new agents built on ADK can register themselves and also programmatically search for other agents. Open registries like Lifie or the upcoming Google Agentspace directory are likely targets for such agent crawlers. In short, ensure your agent cards are registered in known directories (like Lifie Hub or any Linux Foundation A2A project directory) and accessible at the well-known URL.

“Looking for X” Broadcasts: The A2A protocol itself doesn’t have a concept of an agent shouting into the void “I need service X – who can help?”. Instead, it envisions either searching a registry or directly querying known agents. That said, the Agent Registry proposal suggests a search API: clients could query the registry with a natural language need and get back a list of relevant agents
github.com
. For example, a client could ask “which agent can provide multi-chain token prices?” and the registry would return matching agents (based on their Agent Card descriptions)
github.com
. This is more like a centralized search service than a peer-to-peer broadcast. There is no widely-used on-chain broadcast mechanism for agent requests yet. In practice, an autonomous agent wanting a service will query a directory or use an API like the above to find providers. In summary: focus on making your services visible in agent directories and with rich metadata, since agents will find you by searching those indexes rather than by listening for random broadcasts.

2. On-Chain Discovery Mechanisms

Signaling via Blockchain: On-chain events can theoretically serve as “beacons” to alert autonomous agents of new services. The recent ERC-8004 standard (“Trustless Agents”) is explicitly about using blockchains as the discovery and trust layer
eips.ethereum.org
eips.ethereum.org
. It defines an Identity Registry as an ERC-721 contract where each agent or service gets a token (NFT) as a global identifier
eips.ethereum.org
eips.ethereum.org
. Minting an identity NFT for your service thus creates an on-chain record. Agents could scan this registry’s events (e.g. the Transfer/Mint events) to discover new agents as they are registered. The ERC-8004 identity token’s tokenURI points to an off-chain Agent Registration File (a JSON similar to an Agent Card) describing the agent/service in detail
eips.ethereum.org
eips.ethereum.org
. In the example schema, this JSON can list multiple endpoints/protocols the agent supports: A2A .well-known/agent-card.json, MCP endpoints, even an ENS name or DID for the agent
eips.ethereum.org
eips.ethereum.org
. In concept, an agent could retrieve the NFT, follow the tokenURI to get all service details, and immediately know how to interact (via A2A or HTTP, etc.).

Adoption of ERC-8004: Currently, ERC-8004 is very new and experimental. It was proposed in Aug 2025 by contributors from MetaMask, Coinbase, Google, etc., but is not yet widely implemented
eips.ethereum.org
eips.ethereum.org
. You have already deployed an identity registry on Base – but as you saw, yours is one of the only entries. No evidence yet suggests that popular agents are actively scanning these registries (most agents today still rely on off-chain discovery). In fact, ERC-8004 acknowledges that A2A and similar protocols “don’t inherently cover agent discovery and trust,” which is why it introduces on-chain registries
eips.ethereum.org
. So you are on the bleeding edge here. To leverage it better, you’d want to fix the contract bugs (so functions like getAgentInfo() and tokenURI() work), and then publicize this registry in the agent community. If others start registering their agents as ERC-8004 identities, autonomous on-chain discovery becomes more viable. Right now, it’s a bit of a chicken-and-egg: agents don’t monitor the registry because nothing’s there; providers don’t register because no agents listen. Keep your implementation up-to-date with the ERC-8004 spec progress and consider contributing to any reference implementations (for example, the Daydreams project provides a reference library for ERC-8004 and agent trust frameworks
github.com
).

ENS & Naming: Using ENS (Ethereum Name Service) for discovery is an intriguing idea, though not yet standard for agents. ENS could serve as a human-readable pointer to your service’s info – e.g. you could create services.coinrailz.eth and add text records or contenthash pointing to a JSON listing all your service endpoints. In ERC-8004’s registration file schema, they even include an example of an endpoints entry of type “ENS” (e.g. "endpoint": "vitalik.eth")
eips.ethereum.org
. This suggests the concept of using ENS names as part of an agent’s identity. However, for an agent to utilize ENS, it would need to know to resolve that name. Presently, agents are not known to crawl ENS domains systematically. ENS is more likely to be used in a trust context (e.g. verifying an agent’s domain or owner). Still, having an ENS for branding can’t hurt – especially if you plan to support web discovery (an AI agent integrated into a browser might resolve ENS names as websites or data sources). If you do use ENS, document it so that any agent developer can code resolution if needed.

Custom On-Chain Registry Contract: Deploying a custom ServiceRegistry smart contract is possible but note it would be yet another proprietary listing. For instance, you could have a contract where you call registerService(name, URL, metadataHash) and emit an event. Agents would have to know to watch this specific contract’s events. Right now, there is no general on-chain service registry that all agents watch by default. The trend (with ERC-8004) is toward a single canonical registry per chain (a singleton contract)
eips.ethereum.org
. If Base or Coinbase adopts an official identity registry and discovery contract, aligning with that would be ideal. If you create your own, you’ll need to lobby agent developers to incorporate it. The BlockBeats analysis of x402 echoes this: Coinbase’s current Bazaar is off-chain, but “an on-chain directory can be built to allow anyone to list their content for sale (APIs, etc.) and embed a rating system”
theblockbeats.info
. In other words, there is recognized value in on-chain discovery, but it hasn’t been fully realized yet. You could pioneer this by evolving your ERC-8004 deployment or building a simple on-chain list of x402 services. Just be aware of adoption hurdles – it might only pay off if it becomes part of a broader standard or if major players (Base, Coinbase) endorse it.

On-Chain Event Suggestions: If you want to emit on-chain signals in the interim, leverage what you have: for example, your IdentityRegistry could emit a custom event with a summary (agentId, owner, maybe a short descriptor or content hash) whenever a new agent registers. Also, when you add a new service to your platform, you might consider emitting a log from a known contract (perhaps your platform’s own on-chain identity) – e.g. an event NewService(name, endpointURL, price). Agents aren’t listening for that today, but if you document it, any interested developer or future agent could start. It’s akin to how The Graph subgraph discovery works – subgraphs emit events and an indexing service picks it up. Here, you’d hope someone builds an indexing agent for services. In summary, on-chain discovery is forward-looking: support ERC-8004 as it matures (to be part of the wider trustless agent ecosystem), and don’t hesitate to signal via events and ENS – but temper expectations, as most agents currently look to off-chain registries first, not raw blockchain events.

docs.cdp.coinbase.com
docs.cdp.coinbase.com

x402scan vs. Bazaar: To clarify, x402scan is an analytics explorer for the x402 ecosystem (run by the community, e.g. Merit Systems)

The good news: Coinbase intends the Bazaar to be the “Google for agentic endpoints,” enabling “agents to automatically discover and interact with any service added to the ecosystem”

Agent SDKs and Support: Aside from Coinbase’s own SDKs (the CDP JavaScript SDK, etc.), other frameworks are adding x402 support. The Virtuals Protocol (on Base) and Eliza (ai16z) on Solana are cited as “integration frameworks” that support X402

Emitting x402-Specific On-Chain Signals: The x402 system itself mostly relies on off-chain interactions (HTTP status codes, facilitator verification). However, one on-chain aspect is that the facilitator (CDP) likely logs the payment transactions on Base. Agents could theoretically monitor those (for example, to see which services are getting usage). But more directly, Coinbase’s facilitator roadmap mentioned adding “a discovery layer for buyers (human and agents) to find available services”

The first autonomous payments are likely to come from an agent specifically programmed to utilize x402 (perhaps an experiment from Coinbase, Daydreams, or a hackathon project). Making those folks aware of your platform (via documentation or being active in forums/Discord) can accelerate that first usage.

ai16z/Eliza OS (Solana) – This is a decentralized AI agent ecosystem on Solana (often referred to as $AI16Z or now $ELIZA). It created a “bazaar of agents” for trading and finance use cases
aiagentsdirectory.com

Instead, they might communicate through Solana programs or off-chain APIs defined by the Eliza framework. For example, an ai16z agent might be coded with a fixed set of tools (like a trading API or a price feed) rather than dynamically searching the web. However, the concept of what you’re building aligns with their vision. They aim for a “marketplace of trust” for agents

Coinbase CDP / Base Chat Agents – Coinbase’s own ecosystem (Base Apps, XMTP chat agents, etc.) is something you’ve partly integrated with. Base has an example XMTP chat agent with x402 (the Stableburn and Crossmint agents) which can autonomously pay for premium API calls

Other Agent-to-Agent Communication Protocols: Outside of A2A, a few projects exist. 5. Smart Contract-Based Communication

On-Chain Service Registry Contracts: As discussed, one idea is a dedicated on-chain ServiceRegistry contract. This would be a smart contract that holds a list of available services (perhaps mapping service IDs to metadata or emitting events when services are added/updated). In theory, an autonomous agent could periodically query this contract (e.g. call a function getAllServices() or listen to an event feed) to discover new offerings. Today, there is no universal service registry contract deployed on Base or Ethereum for agent services. However, ERC-8004’s identity registry is a step in that direction, serving as a general agent registry. If you feel a bespoke ServiceRegistry would help, you can deploy one – but try to align it with emerging standards. For example, you could deploy an ERC-4824 (Decentralized web services registry) or simply piggyback on ENS+IPFS (store a list of services in an ENS record). Again, the challenge is teaching agents to check there. It might be easier to collaborate on existing proposals like the A2A Agent Registry (which could be implemented as a service or contract). The GitHub proposal in June 2025 outlines a registry service where agents can be “entitled” to clients and an open /agents/public endpoint for discovery
github.com
 – you might run your own instance of this and encourage others to use it.

Event Emission for Capabilities: Emitting on-chain events whenever you add or update a service could, in theory, alert any watchers. For example, if your IdentityRegistry contract is fixed, you could use its agentId tokens to denote different services or just one identity for your platform and then emit a custom event like ServiceAdded(agentId, serviceName, price, metadataURI). If an agent or an indexing bot is listening, it could pick up the new event and then fetch more info from the metadata URI. This pattern is analogous to how NFT marketplaces index new listings or how The Graph indexes subgraph manifests. Currently, no standard event schema exists for “new AI service” – you’d be rolling your own. It’s low-effort to do on your side, though, so it might be worth implementing proactively. Even if no agent listens today, you create a historical on-chain record that could be used later. Additionally, these events could feed into analytics like x402scan or any future on-chain bazaar.

Blockchain Messaging (XMTP) for Announcements: XMTP (Extensible Message Transport Protocol) is like a decentralized pub-sub for web3 (used for wallet chat). Agents with a wallet (which includes most on-chain agents) can send and receive XMTP messages if integrated. One idea is to designate an XMTP topic or public key as a channel for service announcements – e.g. all agents listen to messages from ServiceAnnouncements.eth or on topic “x402-services”. If you publish a standardized message (JSON payload describing a new service and its URL/price) on that channel, any agent connected to XMTP could process it. There’s precedent in AI agent communities for using chat protocols as coordination backplanes (some “AutoGPT”-style agents use Discord or Slack channels to post tasks for others). XMTP could play a similar role in a decentralized way. However, this is an experimental idea – you’d need to coordinate with other developers to adopt a common topic and message format.

On-Chain Job/Request Boards: Another facet of agent communication is a request marketplace: agents in need of a service could post a request, and service agents could respond. This flips discovery around – instead of searching for a service, an agent says “I need X” on-chain, and the matching service finds them. Projects like SingularityNET attempted something like this: they had an on-chain registry of AI services and a process where a consumer could send a request (with payment in their AGI token) to call a service, which the provider would fulfill on-chain. That system, however, was fairly static (services had to be registered in advance). A more dynamic “job board” could be a contract where agents post tasks (maybe with a bounty) and any agent can claim it. To date, we haven’t seen broad adoption of such on-chain job boards in the new wave of autonomous agents – most coordination happens off-chain (e.g. agents delegating to each other via A2A calls, or human-initiated tasks). That said, Keep an eye on emerging protocols for multi-agent coordination. For instance, Pala (Palo Alto Networks) and others discuss agent coordination security
live.paloaltonetworks.com
 which might mention patterns of broadcasting capabilities or needs in a network. If a standard for on-chain requests emerges (perhaps as part of an open agent economy DAO), you could integrate with it.

Summary: There’s currently no single smart-contract-based communication standard for agent discovery or requests. But you can prepare by: (1) Using your on-chain identity contracts to their fullest (emit events, store as much metadata as feasible like registration file URLs or service indices); (2) Experimenting with decentralized messaging (XMTP) to announce updates; (3) Staying involved in multi-agent protocol communities (A2A discussions, Ethereum Magicians threads for ERC-8004
ethereum-magicians.org
, etc.). By doing so, you position your platform to be discovered via any future on-chain mechanism, in addition to the current off-chain ones.

6. Machine-Readable Service Descriptions

Autonomous agents often need structured information about how to use a service. Right now, there isn’t a universal schema like “robots.txt for agents,” but a few approaches exist:

A2A Agent Cards & Skills: Since you already provide A2A agent cards, use the skills section to clearly enumerate each service endpoint as a distinct skill with its inputs and outputs if possible
a2a-protocol.org
. The A2A spec’s AgentSkill can include details like expected input format (text vs JSON) and output types. While not as detailed as an OpenAPI spec, it at least tells an agent what the service does in natural language. For example, a skill entry might be: Name: trending-tokens, Description: “Provides top trending token symbols on specified chain”, Inputs: “chain name (text)”, Outputs: “JSON list of tokens”. This helps any agent that reads your card to programmatically understand capabilities and maybe even do parameter filling.

OpenAPI / Swagger: If your HTTP APIs have OpenAPI (Swagger) definitions, it’s valuable to publish those (e.g. JSON or YAML file) and link to them. An AI agent integrated with an LLM could theoretically ingest an OpenAPI spec to understand how to call the API. For example, OpenAI’s functions and plugin system rely on a manifest and OpenAPI schema so the model can decide how to call the function. We don’t yet have autonomous agents crawling OpenAPI specs on their own, but consider providing it for each service anyway – it aids human developers and any future tooling that converts OpenAPI to agent-readable form. You could either embed it in your agent-card (maybe via a documentation URL field
a2a-protocol.org
) or at least host it on your website (maybe under /api/docs/).

JSON-LD / Semantic Web: Another angle is using semantic descriptions. Outshift’s OASF (Open Agent Services Framework) is essentially a JSON-LD schema for agent and service records
docs.agntcy.org
. It tries to create a “consistent formatting of capability information and metrics”
learnprompting.org
. This is still experimental, but if you want to be thorough, you could create an OASF record for your platform. There’s mention of an Agent Directory powered by AGNTCY using OASF, with a hosted instance at agent-directory.outshift.com
docs.agntcy.org
. Registering there (if it’s open) could give your services visibility to any agents using that directory or semantic search. At minimum, adopting a JSON-LD context for your agent metadata could future-proof it (so agents can query it in a knowledge-graph fashion). For instance, you could label data with schema.org-like tags (if any exist for services or APIs). This isn’t immediately needed, but it’s a 20% experimental effort that could pay off if semantic discovery picks up.

Markup for LLM Agents: Many autonomous agents are essentially LLMs with tools. To cater to them, the more natural-language and explicit your descriptions, the better. Keep service descriptions concise and factual (so an LLM agent doesn’t misinterpret). If possible, provide example inputs/outputs. For instance, in your agent card or docs: “Example: GET /api/trade-signals?pair=ETH-USDC returns JSON like {signal: \"BUY\", confidence: 0.9}.” An agent with an LLM backbone might have been fine-tuned or prompted to seek out such examples when deciding how to use a tool.

Emerging Standards: Aside from A2A and OASF, there’s movement in the W3C and other bodies about describing AI services. Some discussions revolve around using JSON-LD context in the .well-known/ai-plugin.json (for AI plugins) to make them more discoverable by search engines or agents. Keep an eye on initiatives like OpenAI’s Plugins (not autonomous by themselves, but they set a pattern for describing a service to an AI) and LangChain Hub (a hub of tools with their usage info). If a LangChain tools registry becomes popular, you might list your services there with instructions; although LangChain tools usually require some Python wrapper code, which implies human setup, not autonomous discovery.

Bottom line: Continue to publish thorough, machine-readable documentation for each service – whether via A2A agent cards, OpenAPI specs, or JSON metadata.
