4) The decompression fix — high upside, but add guardrails (or you invite trouble)
I like the strategy:


Try all normal decoders first


Only if all fail, attempt decompression


Then retry decoding


That’s a correct layering.
But decompression comes with two real risks:
Risk A: Decompression bombs / resource spikes
A tiny compressed payload can expand massively. If an attacker figures this out, they can burn CPU and memory.
Guardrails to add (minimal, not overengineering):


Max input size (you have 192 bytes now, but enforce e.g. ≤ 4 KB)


Max decompressed size (e.g. ≤ 64 KB)


Timeout / try-catch per attempt


Only try brotli if payload length suggests it (or cap CPU)


Risk B: Brotlis without magic bytes
You noted brotli has no magic bytes and you “try directly.” That means you might attempt brotli on arbitrary garbage every time, which can be expensive.
Better approach (still simple):


Only attempt brotli if gzip + zlib/deflate fail AND the payload is above a minimal length threshold (e.g. > 32 bytes) AND you cap output.



5) Observability: metrics counters are good, but you still need one thing
You added “compressed-gzip/deflate/brotli” counters — good.
But what you need to be able to answer, quickly, is:

Did decompression succeed but inner decoding still fail?

decompress_succeeded: true/false


decompressed_len: N


inner_decode_type: cbor/msgpack/json/eip3009/unknown


That gives you a clean truth table.
