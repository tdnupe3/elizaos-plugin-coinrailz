Payment Verification Architecture Options for Coin Railz
Option 1: EIP-712 Signatures Only (Standard x402-Express)

In this model, Coin Railz continues using the standard x402 flow with EIP-712 signatures for payment authorization. This is the default behavior of the x402-express middleware: when a client receives a 402 response, it creates a signed payment payload (an EIP-712 typed message) authorizing the transfer of the required amount of USDC, and retries the request with that signature in the X-PAYMENT header. The Coinbase facilitator (running on the Coinbase Developer Platform, CDP) then verifies the signature and executes the USDC transfer on-chain (via the EIP-3009 “TransferWithAuthorization” mechanism) on behalf of the client. If valid, the server returns a 200 OK with the resource. All of this happens in a few seconds, gaslessly for the client, since Coinbase’s service covers the gas fee for the on-chain settlement.

Compliance (x402 Bazaar & Discovery): This option fully preserves compliance with the x402 standard. By using the official CDP facilitator and keeping discoverable: true in your payment responses, Coin Railz remains automatically indexed in the x402 Bazaar discovery layer. In practice, nothing changes from your current setup – your endpoints continue to advertise themselves to the Bazaar as pay-per-use services, so AI agents can find them. (The Bazaar specifically ingests services using the Coinbase facilitator with the discoverable flag, which you already have. Sticking to this model means zero risk to your discovery status.)

Agent SDK Compatibility: Option 1 is natively supported by all standard agent SDKs. Libraries like x402-fetch and x402-axios (JavaScript), AgentKit (Coinbase’s AI agent toolkit), and agent platforms like ElizaOS have been built around this EIP-712 flow. For example, Coinbase’s x402-fetch wrapper automatically intercepts a 402 response, crafts the EIP-712 signature, and attaches it on retry – all behind the scenes. Because you’re using the standard middleware, any agent using these SDKs can pay Coin Railz effortlessly. There’s no custom authentication or special-case logic needed; one function call in the agent (e.g. a fetch with the x402 wrapper) will handle the payment challenge and succeed. This means maximum compatibility with existing agents – they will treat your service as a first-class x402 endpoint.

Fit for Autonomous Agents: Relying solely on EIP-712 signed payments is actually designed for autonomous agents. It enables machine-to-machine payments without manual steps. The client agent doesn’t need to manage blockchain connectivity or gas – it only needs to sign a message, which is straightforward with a private key (many agent SDKs use a custodial or embedded wallet for this). The facilitator then handles the blockchain part. This minimizes friction and latency, which is ideal for agents operating in real time. In short, Option 1 aligns perfectly with the x402 protocol’s goal of frictionless, instant payments for AIs.

Security: The standard x402 signature flow is highly secure. The EIP-712 payload (based on EIP-3009) includes a unique nonce and details of the transfer (amount, receiver, etc.), preventing replay attacks or tampering. Once the facilitator uses the signature to execute the transfer, that authorization cannot be reused – the USDC smart contract marks the nonce as consumed. Underpayments are inherently prevented because the server specifies the exact amount required and the signature authorizes that exact amount; a signature for less (or a different recipient) wouldn’t satisfy the verification. Additionally, because the facilitator verifies the signature off-chain and ensures the funds move on-chain to the correct address, there’s no opportunity for a client to “spoof” a payment – they either had the private key to authorize the transfer or not. Coinbase’s facilitator also provides an extra layer of fraud checks and will only settle the payment if everything matches up (correct schema, network, and amount). Overall, sticking with EIP-712 via the official middleware means you’re leveraging Coinbase’s battle-tested security for micropayments.

Pros & Cons: The benefit of Option 1 is its simplicity and reliability. It’s essentially what you have now, so no development effort is required and you retain full compliance and support. The main downside is inflexibility: clients must use the EIP-712 method. If a developer or agent doesn’t integrate the x402 client library or doesn’t have a Coinbase-facilitated wallet, they might find it non-trivial to manually reproduce the signature flow. For example, a person testing with cURL or Postman cannot easily generate the required signed payload without writing code. In the current ecosystem (which is rapidly coalescing around the standard), this is usually fine – most serious users will use the provided tools. But it could slightly hinder adoption by more independent developers or non-standard agents. Additionally, Option 1 means 100% dependence on the Coinbase facilitator service for verification and settlement. If that service has downtime or the client has network issues reaching it, payments might not go through (though the facilitator has been reliable so far). Some projects might also desire a more trustless approach (on-chain proof) for philosophical reasons. Still, given that x402 is specifically designed to offload complexity to the facilitator, sticking with it is generally a solid, low-risk choice.

Option 2: Hybrid – EIP-712 + Raw Transaction Hash

This option would accept both forms of proof: the standard EIP-712 signature and a raw transaction hash as payment evidence. In practice, after a 402 response, the client could either (a) use the typical signed authorization (as in Option 1), or (b) actually send the USDC on-chain to your address and then provide the transaction hash in the X-PAYMENT header. Your server would recognize the hash and verify the payment on-chain, instead of via the facilitator. The endpoint would thus handle either type of X-PAYMENT payload.

Compliance & Discovery: Importantly, this hybrid approach can be implemented without losing x402 Bazaar compliance. You would continue to support the standard EIP-712 scheme and use the Coinbase facilitator for it, which means from the outside nothing changes in how your service is advertised. The 402 response can still list the usual payment requirement (e.g. “USDC on Base, $0.01”) with the standard scheme; the fact that you additionally honor raw tx hashes can be kept as an internal feature or noted in documentation. Because the official flow remains intact, the Coinbase discovery crawler will still index your service normally. In other words, Option 2 is a superset of Option 1: you’re not removing anything, just adding another accepted proof method. Thus, Coin Railz stays fully discoverable in the Bazaar and retains its auto-indexed listing (the listing is tied to using the CDP facilitator and the discoverable flag, both of which you’d still use).

Compatibility with Agent SDKs: All existing agent integrations remain compatible, since they will continue to use the EIP-712 path by default. In a hybrid model, both the Coinbase-style payload (base64-encoded EIP-712 sig) and a format like txhash=... could be accepted. This makes Coin Railz compatible with a wider range of clients, including custom or future SDKs that might emphasize on-chain proofs.

Best for Autonomous Payments: Option 2 aims to cover all bases. Autonomous agents will mostly use the facilitator path (it’s easier and faster for them), so they benefit exactly as in Option 1. Meanwhile, the hybrid model also works for more manual or autonomous-on-chain approaches. For example, consider an AI agent that has a built-in crypto wallet and can broadcast transactions itself (some advanced agents or bots might do this to maintain full on-chain auditability). Such an agent could skip the off-chain facilitator and just pay on-chain, knowing that Coin Railz will accept the receipt. This might not be the mainstream mode today, but your service would be future-proofed for it. Essentially, real agents can continue to operate in the proven way, and the hybrid option doesn’t hinder that at all – it simply also allows on-chain transactions by agents or users who choose that route. By catering to both, you ensure that whichever way autonomous payment trends evolve (fully off-chain authorized vs. direct on-chain), Coin Railz supports it.

Security Implications: Adopting a hybrid model means you’ll need to implement the on-chain verification logic alongside the existing facilitator flow. This introduces several security considerations:

On-Chain Payment Verification: When a client provides a transaction hash in X-PAYMENT, your server must verify that transaction on Base. This involves connecting to a Base node or blockchain API and retrieving the transaction details (and receipt). You’d need to confirm:

The transaction exists and is confirmed (not pending or fake).

It was a USDC transfer (or equivalent) that sent at least the required amount to your designated payment address.

The transfer is valid for the context – e.g., correct network (Base) and correct token (USDC contract). Since your service only accepts USDC on Base, you’d enforce those conditions explicitly.

The transaction hasn’t been used before to access your service (preventing replay).

You will likely parse the transaction’s logs for the Transfer event of the USDC token contract to get the from, to, and value. For instance, if the required price is $0.01 USDC, you check that there’s an event where to == (your address) and value >= 10000 (if USDC has 6 decimals, $0.01 = 1e4 units). If all checks out, you consider the payment fulfilled. This is essentially what a facilitator would do internally if it handled raw transactions – now that responsibility is on your middleware.

Replay and Double-Spend Mitigation: Without the one-time signature security of EIP-712, you must be vigilant about replays in the raw tx mode. A malicious user might attempt to use one transaction hash to satisfy multiple requests. For example, if no safeguards exist, they could pay $0.01 once, then attach the same txhash to ten different API calls and get 10 responses “for the price of one.” To stop this, you need to track which transaction hashes have already been accepted, and reject repeats. This could be done by maintaining a server-side datastore (even an in-memory cache with eviction, or a persistent DB for longer tracking) of tx hashes that were used to unlock content. When a hash comes in, check against the store: if seen before, respond with an error or another 402 (possibly with a message like “payment already spent”). Mark new hashes as used as soon as you accept them (to handle quick successive requests).

Additionally, consider tying payments to request context if possible. In the pure HTTP paradigm, the simplest context is the exact API endpoint/price. Since your endpoints have fixed prices, a transaction of the correct amount to your address is fungible – it could unlock any endpoint with that same price. This raises a scenario: if two different users both need to pay $0.01, one could pay and the other could attempt to reuse that same tx hash. Your tracking of used hashes would prevent the second usage, but note that it doesn’t distinguish who paid – just that someone paid. In effect, the first user’s payment, once accepted, is “consumed” for that hash, and a second user cannot reuse it. That’s desirable, but it implies the first payment can only ever be used once even by the original payer (which is fine for one-off requests).

A subtle attack to watch for is front-running: Suppose an honest agent decides to pay on-chain. They broadcast a transaction and intend to call your API with the hash once it confirms. A malicious actor watching the mempool could see a transaction going to Coin Railz’s address for $0.01, grab its hash after it’s mined, and quickly attempt to call the API with that hash. If they beat the honest agent to it, your server might accept the hash and serve content to the attacker, marking the hash as used. The honest agent’s later request would then fail (since the payment was essentially “stolen”). This is a tricky scenario, but its likelihood depends on how public and valuable your content is. To mitigate this, you could require the transaction to be confirmed and perhaps add a tiny delay to ensure the original sender has time – but an attacker could be just as fast after confirmation. There’s no perfect solution under pure HTTP, except that the agent could have avoided this by using the signature method (which cannot be front-run in the same way, since the payment is not public until it’s verified internally). In practice, this kind of attack is probably rare for $0.01 payments (the attacker would spend time and effort to steal a penny’s worth API call), but it’s worth noting.

Underpayments and Overpayments: The server must ensure the amount in the transaction is sufficient. If someone only sends half the required USDC, that should not unlock the resource. Fortunately, that check is straightforward. Overpayment (sending more than required) is less of a security issue and more of a business logic decision: by default, you would treat any amount ≥ required as fulfilling the requirement (essentially a tip if it’s extra). You might log or communicate in the response if an overpayment was made, but generally one transaction = one resource is simplest. You should not apply one large payment to multiple calls unless you implement a credit system, which is beyond x402’s scope right now.

Maintaining Facilitator Security for Signatures: Your hybrid implementation should ensure that when a client provides the standard signature, you still defer to the facilitator for verification (just as you do now). You wouldn’t try to verify EIP-712 signatures yourself (that would involve recovering the signer and interacting with USDC contracts – essentially reimplementing the facilitator). It’s better to continue using Coinbase’s /verify and /settle endpoints for those. So your logic will branch: if X-Payment looks like a signature payload, pass it to the existing x402-express flow (Coinbase will verify it); if it looks like a tx hash, do the on-chain check yourself. This way, the security of the signature path remains as strong as ever (backed by Coinbase’s infrastructure), and you only handle security for the raw tx path as discussed above.

Overall, while the attack surface does widen slightly by accepting raw transactions, these risks can be mitigated with careful implementation. The x402 spec itself acknowledges that a server may perform its own verification (even on-chain) if capable, which is exactly what you’d be doing. By implementing proper validation (transaction lookup, amount check, one-time use enforcement), Option 2 can be made secure. Essentially, you are combining the trust-minimized approach of on-chain settlement with the convenience of the off-chain standard – as long as each piece is handled by its appropriate mechanism, security remains strong.

Revenue and Conversion: Adopting a hybrid model could improve conversion of potential users without sacrificing the existing agent revenue. All the agents that currently can pay you (via the standard method) will continue to do so – so you’re not losing any usage. On top of that, you’ll start capturing users who until now might have been blocked or turned away by the strict requirement of an EIP-712 signature. For example:

A developer experimenting with Coin Railz might not have set up the Coinbase SDK. They hit your endpoint, get a 402, see the USDC address/amount in the response, and think “I’ll just send USDC and try again.” Today, that yields a 402 again (as you observed). With Option 2, that same experiment would succeed – turning a curious developer into a satisfied (paying) user. This lowers the entry barrier for quick tests or one-off usage.

With hybrid, they can achieve that by using on-chain payment, meaning those types of users would be willing to use Coin Railz whereas they might skip it if it were signature-only.

If executed correctly, this option positions Coin Railz to serve the broadest audience and could differentiate your service as one that is both part of the official ecosystem and friendly to DIY blockchain users.

Security Considerations: Option 3’s security considerations are similar to the raw transaction part of Option 2, except now you have no safety net from the facilitator at all. You must run your own verification and settlement logic:

Option 4 suggests a compromise where you maintain two parallel sets of endpoints: one set continues to use the standard x402-express middleware (EIP-712 + facilitator) for the majority of users, and another set is a custom implementation that only accepts on-chain transaction proofs (similar to Option 3’s method). In short, you ensure full compliance on one interface, and treat the other as a bonus path for those who know about it. This could pull in additional usage that you wouldn’t get if you only had the facilitator route.

The separation can also provide insights: you could track how many calls come through the custom vs. standard routes. If very few use the custom ones, it tells you that the standard method is sufficient for most (and you have the option in future to deprecate the unused route if it’s not worth maintaining). If, conversely, you see significant usage on the custom routes, that validates offering them and you might invest more in that path.

In the near term, it’s likely that the bulk of revenue will still come from the standard x402 usage, since that’s how the ecosystem is oriented. The custom routes might provide a small boost or serve as a safety net for certain users. Option 4’s approach ensures you don’t miss out on any revenue: you cover the common case and the edge cases separately. It’s more work, but potentially more inclusive.

To summarize, Option 4 gives you full compatibility and compliance through one channel, while also enabling a custom-verification channel for additional flexibility. It’s a “belt and suspenders” approach – very thorough, but also more complex to maintain.

Comparison of Options

Discoverability and Compliance: Options 1, 2, and 4 keep Coin Railz in the Coinbase x402 Bazaar. Option 1 and 2 use the official facilitator for all standard requests (ensuring the discoverable: true flag is honored and auto-listing remains). Option 4 preserves a facilitator-backed endpoint for indexing, while adding custom endpoints that aren’t indexed (which is fine, since they’re supplementary). Compatibility with Agent SDKs: Both Option 1 and Option 2 maintain complete compatibility with agent SDKs like x402-fetch, AgentKit, and ElizaOS. These tools all implement the standard EIP-712 handshake, which your service will continue to support in those options. In fact, agents using those SDKs won’t even notice whether you have a hybrid capability – they will just do the normal thing and it will work. Option 4 also maintains this compatibility on its main endpoints, so agents can use the service normally. Only Option 3 breaks this compatibility, because it would present a payment flow that standard libraries do not understand (no signed payload to generate). That would require custom client coding, which the major agent frameworks currently don’t do for x402 (they assume the facilitator model). In short: to work with at least one standard agent SDK (a requirement you noted), you need to keep the standard flow. Options 1, 2, and 4 each do so, whereas Option 3 does not.

 

It’s worth noting that if you implement Option 2 or 4, you might attract use from other emerging SDKs or agent systems that choose to leverage the raw transaction capability. For instance, an agent platform not using Coinbase’s wallet might programmatically handle payments by sending transactions. That platform could integrate with Coin Railz via the raw method. A concrete example is the PayStabl AgentPay approach which defines an X-Payment format with type=ethereum, txhash=..., amount=... for servers that check on-chain receipts. If a developer is using something like that, your hybrid or dual-endpoint setup would be compatible with it (whereas a signature-only service might not be). Thus, Options 2 and 4 potentially make Coin Railz compatible with additional tools beyond Coinbase’s own – all without breaking the Coinbase-based compatibility.

 

Approach for Real AI Agents: From an autonomous agent’s perspective, the smoother the payment process, the better. Option 1 (EIP-712 only) already provides a very agent-friendly experience: no manual steps, no gas, instant verification – agents can autonomously handle it in milliseconds. Option 2 (hybrid) and Option 4 (dual) maintain that same great experience for agents by keeping the standard path available. Real agents will likely default to it. Option 3 (on-chain only) would be the most cumbersome for agents: it introduces waiting for block confirmations and requires the agent to manage blockchain interactions. That’s far from the “instant, automatic” ideal of x402. Therefore, for autonomous agent usage, the approaches that include the facilitator path (1, 2, 4) are clearly superior.

 

Between Option 1, 2, and 4: all three give a top-notch agent experience on the standard flow. The takeaway: don’t remove the facilitator flow if you want real agents to pay you easily.

 

Security and Fraud Risks: We’ve analyzed these in each option above, but to compare briefly:

Options 1 (EIP-712 only): Lowest risk. Relies on well-tested smart contract logic and Coinbase’s infrastructure. Built-in replay protection (via nonces) and exact amount enforcement. No blockchain knowledge needed on your side, so minimal chance of implementation error. The main risk vector is if a user’s private key is compromised or if the facilitator had a bug (both very unlikely scenarios in practice).

Option 2 (Hybrid): Wider attack surface, since it includes all of Option 1’s considerations plus your custom on-chain verify code. You must be diligent with the on-chain part: check transaction details carefully, log any anomalies, and keep the list of used tx hashes to thwart replays. The encouraging news is that none of this is unsolved territory – it’s standard practice in blockchain payment systems to verify transactions by hash. As long as it’s done correctly, the security can be very high. Still, there is a greater operational risk: a mistake in your verification logic could lead to accepting invalid payments or missing valid ones. Testing and perhaps auditing that code will be important.

Option 3 (On-chain only): Similar to the above on-chain considerations, but without any fallback. Every payment relies on your implementation. The risk of error is highest here, because you’ll be building the entire payment handling from scratch. Replay attacks, if unmitigated, could directly cost you (e.g., multiple resources given out for one payment). If your node or blockchain API has an outage or delay, your service might be unable to verify payments, causing failures that agents might not handle gracefully. You become responsible for all blockchain edge cases (confirmations, chain reorgs, etc.). So while secure in theory, it places more burden on you to ensure security.

Option 4 (Dual): Essentially the combined risks of Option 1 and 3, isolated to their respective endpoints. The standard endpoints remain very safe (Coinbase-backed). The custom endpoints carry the on-chain verification risks. One advantage in Option 4 is if something goes wrong with the custom flow (say there’s a bug), it doesn’t directly affect users of the standard endpoints – you could even temporarily disable the custom endpoints while fixing it, and your main service for agents remains live. So there’s a bit of a safety net in having the standard flow always there.

In all cases, underpayments should simply result in a 402 again (with perhaps an error message). Overpayments should be treated carefully; likely you accept them but note that the excess is not counted toward future calls (unless you want to implement a balance system). One could imagine a malicious user overpaying once and then trying to reuse that same transaction hash for subsequent calls claiming “I paid more earlier”. If you mark the hash as used after the first call, they can’t reuse it – even if it had extra value. They effectively donated the excess. This is acceptable design, as it keeps each payment tied to one request. These nuances apply primarily to Options 2, 3, 4 (since Option 1 doesn’t have “overpay” concept – each signature is exact).

 

Revenue Potential in Short Term: Options that keep you in the standard ecosystem (1, 2, 4) are likely to generate the most revenue quickly because they tap into the existing base of agents and devs looking to spend USDC for services. Between those:

So you’re more likely to get usage from risk-averse agents (which might include commercial services, not just hobbyists).

 

Given that Coin Railz already demonstrated on-chain payment success (you mentioned a test $0.01 went through on-chain), the question now is about automated consumption by agents – that implies aligning with agent expectations (the standard). Options 1, 2, 4 all align with that, with 2 and 4 offering a bit more. Recommended Approach: Hybrid Verification (EIP-712 + On-Chain Receipts)

Considering all factors – compliance, compatibility, agent experience, security, and conversion – the best path forward is to implement Option 2: a hybrid model that supports both the standard EIP-712 payment signatures and raw transaction proof verification. This approach preserves everything that is currently working (so it won’t alienate any existing users or agents), keeps Coin Railz fully in line with the x402 standard for discovery, and adds an extra capability that can improve flexibility and user adoption.

 

Why Hybrid? This model strikes a balance between discoverability and openness:

Full x402 Compliance Maintained: Your primary flow remains the official one, so Coin Railz stays listed in the x402 Bazaar index and continues to use Coinbase’s facilitator for fast, gasless payments. Agents crawling the Bazaar will see your service and know it speaks the standard protocol.

Agent SDK Compatibility: Any AI agent using x402-fetch, AgentKit, ElizaOS, etc. will interact with Coin Railz using the EIP-712 signature method as before – no changes needed on their side. They will be able to pay and access your API with one function call, which is critical for adoption.

Extended Audience: By also accepting a transaction hash as proof, you welcome users who might approach the 402 flow differently. For instance, developers who are testing your service or building a custom integration could choose to pay by sending a USDC transaction on-chain and simply provide the hash. Some emerging agent frameworks or tools outside the Coinbase stack might adopt this approach as well. Supporting both means you won’t miss out on potential customers who favor one method or the other.

Autonomous Agent Readiness: Realistically, most autonomous agents in the near term will use the easiest available method – which is the facilitator (gasless) route. The hybrid approach doesn’t hinder that at all; those agents will continue to pay seamlessly. Meanwhile, the on-chain option is there for more advanced or cautious users, ensuring Coin Railz can accommodate more “autonomy” preferences (including fully on-chain payments if an agent developer insists on that for trust reasons).

Security Manageable: While adding on-chain verification does introduce some complexity, it’s manageable with careful coding and is a well-understood problem (essentially performing an on-chain lookup and validation). You can implement safeguards as discussed to mitigate replay and spoofing. The standard EIP-712 path remains as secure as ever, since it’s unchanged. In other words, the hybrid model lets you keep the proven security of the standard flow, and you only need to harden the additional receipt-checking logic which is limited in scope.

Risks and Trade-offs: Implementing the hybrid model does mean more work than sticking to the default. You’ll be running part of the “facilitator” role yourself when handling raw tx proofs. This includes maintaining a reliable connection to Base (to query transactions quickly) and storing some state (used transaction IDs or payment records). However, the benefit is a more robust service that can serve both the x402 ecosystem and users outside it. Importantly, there’s no negative impact on your current functionality: if no one ever uses the raw tx option, everything still works as it does today. If people do use it, then you’ve gained new customers you otherwise would have turned away with a 402. The hybrid approach is essentially additive.

 

Implementation Guidance: Step-by-Step

Keep the Coinbase x402-Express Middleware for Standard Payments: Continue to use the x402 paymentMiddleware in your Express app for all endpoints, configured with your service’s receiving address and prices. Ensure each endpoint’s 402 response JSON still sets discoverable: true and includes the required fields for the facilitator (asset, network, amount, etc.). This way, the Bazaar discovery and standard client SDKs will function uninterrupted.

Augment the Middleware to Handle Raw Transaction Proofs: You can do this by introducing a custom verification layer before or after the x402 middleware:

Intercept incoming requests with an X-Payment header: Check if the X-Payment value looks like a raw transaction reference (e.g., a 66-character hex string starting with "0x"). If so, parse it accordingly (some clients might send just the hash, others might include a prefix like type=ethereum txhash=<hash> – be prepared to handle your chosen format).

Perform On-Chain Verification: Using a Web3 library or an API:

Connect to Base mainnet (e.g., via an RPC URL or provider). Use the transaction hash to retrieve the transaction details and receipt. For example, in Node you might use ethers.js or viem to call provider.getTransactionReceipt(txHash).

Confirm the transaction is successful (status 1) and occurred recently (within an acceptable time window after the 402 was issued).

Verify the payment: If the transaction is a direct USDC transfer, check the receipt’s logs for a Transfer event to your service’s address with at least the required amount of USDC. If the transaction was a contract interaction (e.g., a transfer(address,uint256) call to the USDC contract), decode the input or check events to ensure it was sending USDC to you. The key is confirming that your address was the destination and the value meets or exceeds the price.

Optionally, cross-check the sender’s address if you want to attach some identity to the payment, though this isn’t strictly necessary for one-off payments – it’s mostly about the funds.

Prevent replay/double-use: Maintain a record (in memory or a database) of transaction hashes that have already been accepted. Before accepting a new txhash, ensure it’s not in the used list. If it is, respond with 402/payment required again (and perhaps a message indicating the proof was already spent). If it’s new and valid, add it to the used list immediately (to handle concurrent requests with the same hash).

Bypass or short-circuit the facilitator flow: If the raw transaction proof checks out, you should mark the request as paid. In practice, since the x402 middleware by default will try to verify the X-Payment with the facilitator, you need to avoid that in this case. There are a couple of ways:

Approach A: Invoke your custom check before the x402 middleware. If you detect a valid txhash payment, you could attach something to the request object (e.g., req.paymentVerified = true) and then skip calling paymentMiddleware for this request, instead directly calling the downstream business logic that generates the resource. This might involve some routing logic or conditional next() calls in Express. Essentially, you’d short-circuit the normal 402 handling since you’ve already validated payment.

Approach B: Let the x402 middleware run first, but modify its behavior. If x402-express sees an X-Payment header it doesn’t understand (the raw tx), it will likely return a 402 (since the facilitator will reject an invalid payload). To avoid that, it’s cleaner to intercept beforehand as in Approach A. However, if needed, one could catch the 402 response and then do the on-chain check as a fallback, but that’s more complex. It’s best to handle the known raw format upfront.

Respond with the Resource and a Confirmation: When a raw transaction payment is accepted, return the requested content with a 200 OK. It’s good practice to include an X-Payment-Response header in the response, similar to the standard flow. This can contain a JSON or string indicating the payment was confirmed on-chain. For example, you might include X-Payment-Response: {"txHash": "<the-hash>", "amount":"1000000", "asset":"USDC", "network":"base"} to let the client know the payment reference that was used. This mirrors how the facilitator returns a transaction hash in the response header after settlement. It’s optional but adds clarity for the client (and any debugging).

Advertise Both Methods (Thoughtfully): The initial 402 response that clients receive will be generated by x402-express and will list the accepted payment schemes. Since the Coinbase facilitator path is your official method, it will advertise something like an erc-3009 scheme with USDC on Base. There isn’t a standard field to advertise “raw transaction accepted” in the current spec (and unrecognized schemes might confuse some clients). Therefore, you might choose not to include a second scheme in the 402 JSON, and instead document this capability for developers. In documentation or a developer portal, note that advanced users can pay the displayed address directly and provide the tx hash in the X-Payment header as an alternative to the standard signature. (If the spec evolves to allow a formal dual-scheme listing, you could update the 402 response accordingly, but as of now the safer approach is to keep the machine-readable response standard, and handle the alternate flow implicitly.)

Testing: Rigorously test the hybrid flow:

Use the standard x402 SDK (e.g. x402-fetch or the Coinbase AgentKit) to ensure that a typical agent can still pay and access your endpoints with no issues. This tests that the existing EIP-712 flow wasn’t broken by your changes.

Test the raw transaction path manually. For example, call an endpoint to get the 402 response, note the required payment (and service address). Transfer the exact USDC amount to that address using a wallet (on Base). Then attach the tx hash in the next request’s header and see if you get a 200. Try edge cases like an incorrect amount, an old tx hash, or reusing a hash, and verify the server responds with 402 and an error message as expected.

If possible, simulate a race condition (two requests using the same tx hash) to ensure the second is rejected after the first is accepted.

Monitor and Iterate: Once live, monitor the usage of the raw tx option. If it’s rarely used, it at least isn’t harming anything. If it becomes popular for some reason, you might consider optimizations (caching responses or pre-fetching transaction details to reduce latency, etc.). Also keep an eye on security audits or community feedback around this approach since it’s somewhat custom – you want to promptly patch any loophole discovered.

Stay Updated with x402 Standards: The x402 protocol is evolving. By supporting both methods, Coin Railz is somewhat ahead of the standard curve. Keep track of the x402 spec updates or community discussions; it’s possible that future versions may officially incorporate a way to accept raw transactions or other schemes. For example, if an “on-chain receipt” scheme gets standardized, you could formally declare it in your PaymentRequirements. Being involved with the x402 open-source project (perhaps contributing your hybrid approach as a feature request) could even help standardize this, which would benefit all.

Library and Agent Framework Compatibility: With the recommended hybrid approach, all major agent frameworks remain compatible:

Coinbase’s Agent SDKs (AgentKit, etc.) – will continue using the EIP-712 path via the facilitator, so they will work out-of-the-box with no changes.

x402-fetch / x402-axios – these will still trigger the signed payment flow automatically on a 402 response. From the service’s perspective, those payments come in exactly as before and are verified by Coinbase’s backend. The presence of your custom logic won’t affect these clients (except that you must ensure your middleware doesn’t erroneously interfere with a valid signature payload – hence the check for a hex format vs base64 to distinguish them).

ElizaOS and other agent platforms – if they have adopted the x402 standard, they will behave like any other client, using the standard method. Thus, they’ll be fully supported. If in the future some platform like Eliza or others decide to support direct on-chain payments, your service will be ready for them as well.

Custom integrations – Developers using other languages or frameworks (Rust, Python, etc.) without the official SDK can choose: either implement the EIP-712 signing (there are libraries, e.g., using eth-account in Python or viem in Node as Coinbase docs suggest) – or simply use your raw payment option for a simpler but synchronous on-chain flow. By offering both, you cater to both types of developers.

Real-World Example: While the hybrid approach is somewhat new, we can see precedents of services exploring similar ideas. For instance, the PayStabl AgentPay documentation shows an X-Payment header format for Ethereum where a client provides a txhash and amount as proof, indicating some services expect the server to verify on-chain. Your approach would align with that mindset while still maintaining the official Coinbase-supported method. As long as the service remains secure and easy to use for the majority of agents, this could be a selling point.
