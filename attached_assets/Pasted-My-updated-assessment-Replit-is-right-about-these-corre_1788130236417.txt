The MCP server/discover issue is real—with an important qualification

I verified Replit’s assertion against the official specification.

The MCP 2026-07-28 specification says servers implementing that revision must implement server/discover.

But the obligation is version-specific:

Servers implementing MCP 2026-07-28 must support it.

A server remaining on an older MCP protocol revision is not automatically noncompliant merely because it lacks server/discover. Modern clients are expected to detect that and potentially fall back to the legacy initialization flow.

Therefore, Coin Railz has two valid paths:

Properly support the 2026-07-28 revision, including server/discover; or
Correctly advertise and serve an older supported version, with proper fallback behavior.

The worst position is the current apparent middle ground: rejecting server/discover while also handling unknown requests or version negotiation in a way that prevents modern clients from falling back cleanly.

One issue in Replit’s revised test plan

Replit proposes testing:

initialize, server/discover, tools/list, unpaid tools/call, and paid tools/call as one lifecycle.

That is not quite correct for the new protocol.

The 2026-07-28 revision removes the old initialize/initialized handshake. These should be tested as two separate compatibility lanes:
